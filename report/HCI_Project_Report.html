2. Introduction

2.1 The Application

SecureBank is a fictional retail banking application used as the case study for this project. The application represents a typical mobile banking service offered by a commercial bank in Pakistan. It allows customers to view account balances, transfer money, pay utility bills, manage debit and credit cards, review transaction history, and contact support from a single mobile interface.

The project considers a mobile-first application because most banking interactions in the target environment now begin on a smartphone. The same interaction flow could also be delivered through a responsive web interface; the design decisions in this report apply to both platforms.

2.2 Purpose of the System

The system lets customers complete routine banking tasks — checking balances, transferring money, paying bills, controlling card security, reviewing records, and getting help — quickly, securely, and without visiting a branch or waiting on a telephone line. Every screen in this report is judged against that single goal.

2.3 Problems and Needs Addressed

The design addresses several practical problems reported by banking customers:

2.4 Scope and Approach

The project contains two complete variants of the same nine-screen flow: a Good HCI Design that applies usability and accessibility principles, and a Bad HCI Design that intentionally violates them so the resulting problems can be analysed. Both cover identical tasks, so the comparison in Section 6 is like-for-like. Design work followed four stages — identifying users and context, defining functional and non-functional requirements, building a consistent visual system and layouts, then reviewing both variants against Shneiderman's eight golden rules, HCI interaction models, information-display and data-entry guidelines, distributed-interface considerations, and quality-of-service requirements.

4. Good HCI Design

4.1 Design Overview

The good design follows a concept called "calm banking". Each screen answers one question and offers one primary action. The user should always know three things: where they are, what the system is doing, and what will happen next. The design therefore favours visible labels over icons alone, a predictable bottom navigation bar, a review step before any irreversible action, and plain-language feedback.

The interaction model mirrors the real-world mental model of banking: accounts → transfer → review → confirm → receipt. The interface uses a familiar conceptual model (Section 4.4.2), keeps the same terminology throughout, and never hides essential information such as fees or available balance. The result is a flow that a first-time user can complete without training and a frequent user can complete in a few taps.

Three rules guided every screen:

  1. One primary action per screen. Secondary and destructive actions are visually quieter and separated.
  2. Verify before commit. Money movements are reviewed, confirmed with an OTP, and followed by a receipt.
  3. Never rely on memory. Labels, summaries, saved beneficiaries, and step indicators remove the need to remember previous screens.

Navigation follows the same model: a bottom bar of five stable destinations, each containing a short linear task flow rather than deep, unpredictable menus.

TabContainsExample flow
HomeBalance, quick actions, bill reminder, recent activity.Home → Transfer → Review → OTP → Success
PaymentsSend money, bills, scheduled payments, history.Payments → Bill → Review → Success
CardsCard visual, controls, freeze, report lost.Cards → Freeze → Toast → Unfreeze
SupportHelp topics, live chat, tickets.Support → Chat → Transcript
ProfilePersonal details, security, accessibility, language.Profile → Text size → Live preview

Across all screens the back action never discards entered data without asking, the current tab remains highlighted, the step indicator shows progress in multi-step tasks, and irreversible actions always require an explicit confirmation.

4.3.1 Login Screen

Purpose: Authenticate a returning customer, prevent unauthorised access, and reassure the user that the app is trustworthy.

Layout and navigation: A single column with 24 px side margins: brand and language selector, a short welcome heading, the labelled account/CNIC and password fields (each with a visibility toggle and inline validation with an attempt counter), the "remember this device" and "forgot password" row, the primary login button, a fingerprint shortcut, a security note, and a registration link — with no promotional banners competing for attention. Successful login continues to the dashboard, or to the OTP step on an untrusted device; "Forgot password" opens recovery, "Open an account" starts registration, and the back gesture exits without losing the typed account number.

Design decisions: Labels sit above the fields rather than inside them, so they remain visible while typing. The error message explains what happened and how many attempts remain, rather than showing a technical code. The show-password control reduces typing errors on small keyboards. "Remember this device" is off by default because shared devices are common. The fingerprint option is a shortcut for frequent users while the password remains available for everyone. The security note addresses phishing anxiety and builds trust.

4.3.2 Home Dashboard

Purpose: Answer the two questions customers open a banking app for: "How much money do I have?" and "What needs my attention?" — within a few seconds.

Layout and navigation: A greeting and avatar, a full-width balance card with a hide/show control, masked account number and "updated just now" indicator, then four quick-action tiles (Transfer, Pay bill, Scan QR, Top-up), an upcoming-bill reminder, and three recent transactions with icons and status. The five-item tab bar stays visible, switching between Home, Payments, Cards, Support, and Profile without losing state; quick actions open their flow directly, "See all" opens history, and any row opens its detail sheet.

Design decisions: The balance is the largest element on the screen, while the date and "updated" note are deliberately secondary. Only three recent transactions are shown to avoid clutter; the rest are one tap away. The eye control supports privacy in public places. The upcoming bill is surfaced before promotions would be, because it is the action most likely to prevent a late fee. Status labels ("Completed", "Processing") accompany colour so that meaning does not depend on colour alone.

4.3.3 Fund Transfer

Purpose: Collect the recipient, amount, and timing of a transfer with minimal effort and minimal chance of error.

Layout and navigation: A three-step indicator, source-account card, a horizontal row of beneficiary chips (including "New"), an amount card showing the available balance and fee, a "send now / schedule" segmented control, an optional note field with a character counter, and a sticky full-width "Continue" button. "Continue" opens the review screen; the back arrow returns to the dashboard with entered data intact; "New" opens the beneficiary form while a saved person is selected immediately.

Design decisions: The flow is split into three steps so that the user is not asked to verify and confirm on the same screen. Saved beneficiaries support recognition over recall. The fee and arrival time are shown before the user commits, avoiding surprise charges. The amount uses a numeric input with a fixed currency label, and the available balance is repeated so that the user does not have to remember it. "Continue" is used consistently rather than mixing "Submit", "Proceed", and "Next".

4.3.4 Review, OTP, and Confirmation

Purpose: Give the user a final opportunity to verify the transfer, then verify their identity before the money leaves the account.

Layout and navigation: A summary card with recipient, source, amount, and fee rows plus a highlighted total, an irreversibility warning, and a bottom sheet with six OTP cells, a resend timer, "Confirm transfer", and "Cancel"; the dimmed summary stays visible behind the sheet. Editing a row returns to that field with data intact, "Cancel" closes without sending, and confirmation leads to a success screen with a reference number, "Download receipt", "Done", and "Send another".

Design decisions: Separating review from entry is a strong error-prevention measure, especially for irreversible transfers. The amount is the most prominent value in the summary because it is the detail users most often need to confirm. The warning states plainly that a transfer cannot be reversed, which sets accurate expectations. The OTP has a visible timer and a resend option so the user is never stuck. Closure is provided by a dedicated success screen with a reference number and a receipt, rather than a toast that disappears before it can be read.

4.3.5 Transaction History

Purpose: Help the customer find a specific transaction, confirm that a payment was received, and obtain a record for personal or business use.

Layout and navigation: A search field, scrolling filter chips (All, Money in, Money out, Bills), and transactions grouped under date headings, each row showing an icon, description, time, amount, and written status; a statement download in the app bar offers a date range and file format. Tapping a row opens a detail sheet and back returns to the same scroll position, with the Payments tab still selected.

Design decisions: Grouping by date reduces a long list to manageable chunks. Dates and currency use one format throughout. Status is written in words as well as marked with a dot, so the meaning survives colour blindness and grayscale printing. Search accepts either a name or an amount, matching the two ways customers usually remember a payment. The most recent 30 days are cached for offline viewing, which supports the asynchronous side of mobile banking.

4.3.6 Bill Payment

Purpose: Let the customer pay a recurring bill in a few steps and see the due date before it becomes a late payment.

Layout and navigation: A biller search field, a four-item category grid, a "Saved billers" list showing consumer number, due date, and amount with selection state, a contextual note, and a sticky "Continue" button. Selecting a biller opens its payment form, followed by review and success; "Manage" opens the saved-biller editor and back returns to the category list.

Design decisions: Saved billers remove the need to remember long consumer numbers. The due date is shown at the same level as the amount because it drives urgency. The helper note explains where the consumer number is printed, which prevents the most common bill-payment error. Fees are shown before confirmation. AutoPay is available but never enabled silently.

4.3.7 Card Management

Purpose: Give the customer immediate control over card security without calling the bank or visiting a branch.

Layout and navigation: A card visual with an active/frozen status pill, a grouped list of labelled switches (online payments, contactless, show PIN, freeze card), and a visually separated "Report lost or stolen" danger zone. Toggles apply immediately with a short toast, "Freeze card" can be reversed on the same screen, "Report lost or stolen" opens a confirmation and replacement flow, and the Cards tab stays active.

Design decisions: Every switch has a label and a description, so the user knows what will change. Freeze is reversible and clearly separated from the permanent "Report lost" action, which prevents accidental cancellation. The PIN is never shown without re-authentication. The same words ("Freeze", "Report lost") are used throughout, avoiding the common mix of "lock", "block", "disable", and "suspend".

4.3.8 Profile and Accessibility Settings

Purpose: Let users adjust readability, language, security, and notification preferences without hunting through a long list of unrelated options.

Layout and navigation: A compact profile header followed by four labelled groups — Accessibility, Security, Language, and Account — with a text-size slider showing its value and a live preview, high-contrast and reduce-motion switches showing their state, two-factor and change-password rows, an English/اردو segmented control, and a separated logout button. Each row opens a focused subpage or changes the setting immediately with a brief confirmation, and logging out requires confirmation and returns to the login screen.

Design decisions: Settings are grouped by task rather than listed flat, which reduces scanning time. The slider shows a value and affects a live preview, so the user can see the result before leaving. Destructive or session-ending actions are kept away from everyday preferences. Urdu is offered alongside English, and the layout supports right-to-left text. Nothing is hidden behind a "Save" button that gives no feedback.

4.3.9 Help and Live Support

Purpose: Resolve a customer's problem through a real-time conversation, while still offering a reliable path when no agent is available.

Layout and navigation: An agent card with presence and expected reply time, a conversation area with distinct incoming and outgoing timestamped bubbles, a typing indicator, quick-reply chips, a security banner, and a message composer with attachment and send controls. Back returns to the Support tab with the conversation preserved, "End chat" offers to email a transcript, and an offline agent switches the interface to a ticket with an expected response time and a reference number.

Design decisions: The screen combines a synchronous channel (live chat) with an asynchronous fallback (ticket and email), which reflects the distributed-interface model. Presence and wait time set expectations instead of leaving the user guessing. Incoming and outgoing messages are visually distinct, and timestamps make the sequence clear. The typing indicator provides feedback during a delay. The security banner prevents the most dangerous support interaction: sharing an OTP with someone who claims to be from the bank.

4.4.2 Shneiderman's eight golden rules

Golden ruleImplementation in the good design
1. Strive for consistencyThe same colours, spacing, button styles, and terms are used on every screen; primary actions are always filled, secondary actions outlined, destructive actions red.
2. Enable frequent users to use shortcutsFingerprint login, quick-action tiles, saved beneficiaries, and saved billers shorten repeated tasks.
3. Offer informative feedbackInline validation, loading states, "Processing" status, OTP timer, typing indicator, toasts, and the success receipt.
4. Design dialogs to yield closureEach flow ends with a clear result: a success screen, a reference number, and a receipt or transcript.
5. Offer simple error handlingMessages are written in plain language, identify the field, and explain how to correct it; technical codes are never shown to the customer.
6. Permit easy reversal of actionsUsers can edit before confirming, cancel a transfer before sending, unfreeze a card, and leave settings without saving.
7. Support internal locus of controlThe user initiates every action; the system never auto-selects a beneficiary, auto-enables AutoPay, or commits a payment without confirmation.
8. Reduce short-term memory loadVisible labels, a summary of the transfer, a step indicator, saved payees, and a persistent balance remove the need to remember previous screens.

4.4.4 Information display and data entry

The interface applies the information-display guidelines of relevance, clarity, consistency, visual hierarchy, chunking, formatting, and accessibility. Only task-relevant information is shown, headings and amounts are emphasised by size and placement, long lists are grouped by date or category, and all dates and amounts use one format.

Data entry follows the complementary guidelines: minimum input (saved beneficiaries, saved billers, biometric login), immediate validation, contextual help (where to find the consumer number), appropriate input methods (numeric keypad for amounts, date selection for scheduling), consistent field design, and constraints that prevent invalid characters or amounts above the available balance.

4.4.5 Distributed-interface and quality-of-service considerations

Banking is a distributed interaction: the phone, the bank server, the payment network, and the recipient's bank are separate systems. Live support chat is synchronous and shows presence, wait time, and a typing indicator. Transfers, bill payments, and history are asynchronous: they show a pending state, refresh when the connection returns, remain readable for the last 30 days offline, and use an idempotency reference so that a dropped connection cannot debit the customer twice.

Quality of service is treated as part of the interface, not only as a backend concern. Login should respond within two seconds and a transfer confirmation within three, any operation longer than 300 ms should show a skeleton or progress indicator, and errors should be friendly and actionable ("We could not reach the bank. Your transfer was not sent. Try again.") rather than a blank screen or a technical code.

5. Bad HCI Design

It is not a random collection of errors: each flaw was chosen to demonstrate a specific usability or accessibility failure, and each is analysed below. The same nine tasks are covered so that the two variants can be compared directly. The bad version represents a legacy banking portal that has grown by adding features without a design system, rather than a deliberately unusable parody.

The dialog offers no edit, cancel, or timeout information.User controlUsers feel trapped and may abandon the app, then repeat the transfer through another channel.

5.1.5 Bad Transaction History

Overall impression: The screen is a wall of text. There is no search, no grouping, and no reliable way to distinguish money in from money out.

Twenty-two transactions are listed in one continuous block at 7.5 px, with no grouping by date or type.Chunking; readability; cognitive loadUsers cannot scan the list. Locating one payment requires reading every row and often results in failure.

There is no search, filter, or date-range control; only an account dropdown and a free-text period box.Recognition; flexibility; efficiencyUsers must remember when a transaction occurred and scroll manually. Business users cannot find a payment quickly.
A disabled "Loading..." button sits at the bottom and provides no feedback or pagination.Feedback; visibility of system statusUsers do not know whether more records exist or whether the list has finished loading, so they keep waiting or leave.

5.1.6 Bad Bill Payment

Overall impression: The form is dominated by an open dropdown of dozens of companies, while the payment action is nearly invisible and the fee information is unreadable.

6. Comparison: Good vs. Bad HCI Design

The table below compares the two variants across the aspects that matter most in a banking interface. Each row is based on specific evidence in Figures 4.1–4.9 and 5.1–5.9.

HCI aspectGood designBad design
NavigationFive labelled bottom tabs; each task is at most three steps; back preserves data.Eight unlabeled header links and eight abbreviated bottom items; no clear hierarchy or path.
Visual hierarchyBalance is the largest element; one primary action per screen; secondary information is quieter.Sixteen equal tiles, three advertisements, and a 7 px balance; nothing stands out.
Layout and groupingWhite cards on a light background, 8-point spacing, clear sections, and generous whitespace.Cramped tables, inconsistent margins, unrelated items adjacent, and content that overflows.
Typography and readabilityLato, 16 px body text, 1.5 line height, strong contrast, and consistent styles.6.5–9 px text, mixed serif and sans-serif fonts, and long unstructured paragraphs.
Colour and contrastNavy, teal, green, amber, and red used semantically; 11.5:1 on primary buttons; colour is never the only signal.Low-contrast grey text, red for credits and green for debits, and colour-only status dots.
ConsistencyOne design system, one set of terms, and the same button hierarchy throughout."Submit / Proceed / Continue", "Freeze / Lock / Block", and five date formats in one product.
FeedbackInline validation, loading states, OTP timer, typing indicator, success receipt, and status labels.Technical error codes, "may or may not have completed", a disabled loading button, and no receipt.
Error preventionReview screen, OTP, saved beneficiaries, limits, constraints, and confirmations for destructive actions.Preselected bank, no review, "Yes / No / Maybe", no confirmation, and destructive actions next to safe ones.

The comparison shows that the difference between the two variants is not primarily aesthetic. The bad design fails at the level of task completion: users cannot reliably find the balance, confirm a transfer, pay a bill, protect a card, or obtain help. The good design treats each of those tasks as a short, visible, reversible-where-possible sequence with clear feedback at every step.

7. Design Tools

Figma was used as the primary design and prototyping tool because it supports reusable components, variants, auto layout, and clickable prototypes — everything needed to keep nine screens consistent and to demonstrate the navigation between them. Screens were rendered at a 390 × 844 px mobile viewport using the same layout specifications, colours, and type scale as the Figma file.

  • Figma — editable high-fidelity screens, components, variants, auto layout, and clickable prototypes for both variants.
  • Stark plugin — contrast checking against WCAG AA before export.
  • Lato typeface — readable humanist sans-serif across both variants (the bad variant deliberately mixes fonts).
  • Material-style outline icons — a consistent 24 px set, never the only label for a critical action.
  • 390 × 844 px viewport — the standard phone frame for all eighteen screens.
  • Google Forms or Maze (optional) — short usability feedback such as time-on-task and preference ratings.

The Figma file has four pages — 01 Good Design, 02 Bad Design, 03 Components and Styles, and 04 Flows and Prototype — with components shared across screens so that the comparison between variants stays fair.

8. Conclusion

This project designed the same online banking application twice: once with good HCI practice and once with deliberately poor practice. The good design shows that banking usability comes from a few disciplined decisions — one primary action per screen, visible labels, a consistent visual system, a review step before irreversible actions, plain-language feedback, and accessibility built in rather than added later. The bad design shows that the opposite choices do not merely look unattractive: they stop customers completing essential tasks and can create financial and privacy risks. Many of the most serious failures are not visual at all — a preselected destination bank, a "Yes / No / Maybe" confirmation, a missing receipt, or a PIN shown without re-authentication — which confirms that error prevention, closure, user control, and visibility of system status are practical banking requirements rather than abstract theory. Future work would test both variants with five to eight representative users through a think-aloud walkthrough of the transfer and bill-payment flows, measure task completion time and error rate, and compare System Usability Scale scores.
