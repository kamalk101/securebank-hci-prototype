SecureBank: two builds, five tasks, one score.

The same nine-screen banking app exists twice. One applies the design principles from the report; the other breaks them on purpose. Each build is standalone, includes a presenter console, annotations, a task sheet, a SUS questionnaire, instrumentation, and exportable data.

Department of Software Engineering · Mehran University of Engineering and Technology, Jamshoro

Good design

Open the good build

Clear hierarchy, visible feedback, error prevention, and accessible controls.

  • Login, transfer, bills, cards, history, support
  • Inline validation and confirmation before committing
  • Offline, timeout, skeleton, and long-name states

 Bad design

Deliberate violations kept for comparison, not a pattern to copy.

Run a session

  1. Open one build and enter the participant code in the console.
  2. Start task T1–T5 in the task sheet, reading each task aloud.
  3. Let the participant think aloud; do not point at the screen.
  4. Score the SUS, then download JSON and CSV.
  5. Clear the log before the next participant.

Presenter keys

  • 1–9 jump to a screen, ← → step
  • A annotations, C clean phone
  • T tasks, S SUS, D data, E edge states
  • R restart, ? help, Esc close
No build step, no server required. Each folder is self-contained: open good/index.html or bad/index.html directly, or serve the folder over HTTP. Data is stored in this browser only; download it before clearing browser storage.
